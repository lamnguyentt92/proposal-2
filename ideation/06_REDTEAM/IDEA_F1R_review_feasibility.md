- Feasibility findings (per item checked, with evidence and links):

  **F0. Scope, method and verdict.** **Verdict: feasible with changes.** Role: feasibility auditor (technical, ethical, resource). Date: 2026-11-20. Team size, person-weeks and deadlines are out of scope and were not judged.
  - How the evidence was obtained: repositories were cloned and read on 2026-11-20 (AndroidWorld commit `55ddaf5`, 2026-10-23; MobileWorld `5d9dd9d`, 2026-11-18; Android-Lab `4bfe108`, 2025-08-18; MobileSafetyBench `d775aa4`, 2026-01-27; side-effect-loopholes `84b02dc`, 2026-11-15; agent-diff `3bb9c40`, 2026-07-01; UI-TARS `582f3a7`; MAI-UI `3deabf1`). Model sizes and licences come from the Hugging Face API. Papers were read through alphaXiv. **Nothing was executed**: the review sandbox has no `/dev/kvm` and no `vmx/svm` CPU flag, so every statement about the emulator is from code and documentation, not from a run. The GitHub API was not available, so issue trackers were not read.

  **F1. AndroidWorld environment — obtainable, no GPU needed, needs KVM.** <https://github.com/google-research/android_world>
  - Licence Apache-2.0 (`LICENSE`). 116 task templates over 20 apps (`README.md`; `android_world/task_metadata.json` has 116 entries: 61 easy, 36 medium, 19 hard).
  - Device: AVD Pixel 6, system image Tiramisu API 33, `google_apis;x86_64` (`Dockerfile`), started from the command line with `-no-snapshot -grpc 8554`. README states a footprint of 2 GB memory and 8 GB disk per emulator.
  - Headless and Docker: supported but labelled experimental. `docker run --privileged`; `docker_setup/start_emu_headless.sh` uses `-no-window -memory 2048 -gpu off` and turns acceleration on only when `/proc/cpuinfo` shows `vmx|svm`; the script itself warns the image was tested only on Linux with KVM. So: x86-64 Linux host with KVM (or a native arm64 AVD on a Mac); **no GPU for the emulator**. On Apple Silicon the Docker route runs an x86 emulator inside an emulated Linux and is slow (README).
  - Practical consequence: many rented GPU machines/containers do not expose `/dev/kvm`. Plan for the emulator host and the GPU host to be different machines; open models are reached over an OpenAI-compatible HTTP endpoint, so this is not a blocker. `00_CONSTRAINTS.md` still lists the testbed as undeclared — the author must confirm a KVM-capable Linux box (about 16 GB RAM for four parallel emulators; `run.py` takes `console_port` and `grpc_port`, so several emulators can run side by side).
  - Root: the container entrypoint runs `adb root`; `adb_utils.set_root_if_needed` and `execute_sql_command` (`sqlite3 <db>` over `adb shell`) are used by the checkers themselves. The `google_apis` image permits root; a Play Store image would not.

  **F2. Task initialisation, teardown and snapshots — this is where the idea meets resistance.**
  - `TaskEval.initialize_task` (`task_evals/task_eval.py`) resets the device clock to a fixed October 2023 time and calls `app_snapshot.restore_snapshot` for each app of the task. That function (`utils/app_snapshot.py`) force-stops the app, wipes `/data/data/<pkg>`, copies back a stored copy from `/data/data/android_world/snapshots/<pkg>`, then runs `restorecon` and `chmod 777`. One snapshot per app; a missing one is logged and skipped.
  - SQLite task families (`common_validators/sqlite_validators.py`) clear the target table before and after each task and insert their own noise rows; file tasks call `clear_device_storage`; Markor tasks clear the Markor directory. `tear_down` repeats the wipe.
  - Whole-device (AVD) snapshots are not used by AndroidWorld (it passes `-no-snapshot`). The emulator itself supports `adb emu avd snapshot save/load` — MobileWorld (`docs/configure_avd.md`, snapshot `init_state`) and MobileSafetyBench (`environment.py: reset(snapshot_name=...)`) rely on it. Whether AndroidWorld's accessibility-forwarding gRPC channel survives a snapshot load is unknown and must be tested.
  - **Consequence for R1–R3:** "T ; T⁻¹" does not exist off the shelf. If the second leg is started the normal way, its initialisation erases what the first leg did. A chained-leg harness is required: leg 2 must skip the wipe/restore, take `before` from the live state, and have its parameters bound to leg 1's (e.g. `DeleteMultipleRows` sets `rows_to_delete = before[-n:]` and raises if the row count is not exactly `n_rows + n_rows_noise`). This is roughly 30–60 lines per checker family and is doable, but leg 2 is then graded by the shipped `is_successful` under a **non-shipped initialisation**. That must be disclosed and validated with gold round-trips, or a referee will attribute violations to the harness.

  **F3. How much of the suite is actually redundant (card risk 1, now checked in the repository).** From the 116 templates:
  - Natural inverse pairs with a shipped checker on both sides: calendar add ↔ delete (`SimpleCalendarAddOneEvent*` ↔ `SimpleCalendarDeleteOneEvent`/`DeleteEvents`), expense add ↔ delete (single and multiple), recipe add ↔ delete (single and multiple), `MarkorCreateNote` ↔ `MarkorDeleteNote`, `MarkorMoveNote` and `FilesMoveFile` with source and destination swapped, Wi-Fi on ↔ off, Bluetooth on ↔ off, brightness max ↔ min (inverse only if the start is the opposite extreme), and note edit ↔ `MarkorChangeNoteContent`. That is about **9–12 pairs touching roughly 25–30 templates**.
  - No inverse exists for SMS sending (irreversible), `ContactsAddContact` (no delete-contact task), camera and audio recording, OsmAnd, Retro Music and VLC playlists, Simple Draw, or the browser games.
  - So the "decisive experiment on ~15 task pairs" already exceeds what the suite offers natively. Writing new inverse tasks is possible but then the audited checker is the authors' own, not the benchmark's.
  - **Cheap relation the card does not use:** 19 templates carry the `information_retrieval` tag (Joplin, Tasks, OpenTracks, calendar questions). They are read-only by specification, so *any* persistent change during a passed run is an unrequested effect. This needs one leg, no composition, no inverse task and no modified initialisation. I recommend adding it as R0; it roughly doubles coverage.
  - **Checkers are less blind than the card assumes.** `validate_rows_addition_integrity` and `validate_rows_removal_integrity` already verify that no other row of the target table was added, removed or altered. For calendar, expense and recipe pairs a passed leg therefore already certifies the target table; a violation can only come from other tables, other apps, files or settings. The weakly checked families are the file-based ones (`CreateFile`/`MoveFile`/`DeleteFile` look only at the named file), the single-key settings toggles, and the checkers that read the UI tree (clock, contact draft, browser). This bears directly on C1's 3% threshold: with about ten template clusters, a task-clustered 95% lower bound above 3% needs violations that are both frequent and spread over several templates.

  **F4. State observation — feasible for the open-source apps, noisy for the rest; no server-side state.** Storage locations taken from checker code:
  - Per-app SQLite, readable as root: Simple Calendar Pro (`databases/events.db`), Pro Expense (`accounting.db`), Broccoli (`databases/broccoli`), Tasks (`databases/database`), OpenTracks (`database.db`), Joplin (`joplin.sqlite`), Retro Music (`playlist.db`, `music_playback_state.db`), VLC (`app_db/vlc_media.db`), OsmAnd (`map_markers_db` plus files under `Android/data/net.osmand/files`).
  - System providers: SMS (`com.android.providers.telephony/databases/mmssms.db`, also `content query content://sms/...`), contacts (`content query`), call log.
  - Shared storage: Markor (`/storage/emulated/0/Documents/Markor`), Files, gallery/draw (`Pictures`, `DCIM`), audio recorder (`Android/data/com.dimowner.audiorecorder/files/Music/records`), `Download`.
  - Settings keys via `settings get` (Wi-Fi, Bluetooth, brightness).
  - Not persistent state at all: stopwatch/timer and contact-draft tasks (graded from the accessibility tree), browser tasks (page state in Chrome), clipboard (read through the clipper app), `OpenAppTaskEval` (foreground activity). A state diff cannot see what these checkers grade.
  - No remote backend: all AndroidWorld apps work offline; the only downloads are APKs and app data from a Google-hosted bucket (`storage.googleapis.com/gresearch/android_world`, `env/setup_device/apps.py`).
  - Engineering points that decide the noise mask: (a) WAL-mode databases need a force-stop and a copy of `-wal`/`-shm` (AndroidWorld's own `sqlite_utils` closes the app and pulls the file); (b) Google system packages, media scanner and usage stats write continuously, so a whole-device diff is hopeless — restrict the observer to benchmark apps, the two providers, shared storage and settings; (c) after add-then-delete, row ids, `sqlite_sequence` counters and file mtimes differ from the start state, so "state ≈ start" needs semantic normalisation or every gold round-trip is a violation; (d) `restore_snapshot` rewrites permissions, so permission bits must be masked. The ≤ 2% false-alarm precondition looks reachable for app databases plus shared storage, not for the whole device.

  **F5. Agents that can be run today.**
  - Shipped in the repo (`android_world/agents`, `run.py`): M3A (screenshot + set-of-marks), T3A (text-only accessibility tree), SeeAct, a random agent and a human agent. Back-ends in `infer.py`: `GeminiGcpWrapper` (default `gemini-1.5-pro-latest`) and `Gpt4Wrapper` (default `gpt-4-turbo-2024-04-09`); the README itself calls the default legacy and expensive. There is no Anthropic wrapper; one is a small subclass of `LlmWrapper`/`MultimodalLlmWrapper`. "2–3 API models × 2 scaffolds" is therefore available as {M3A, T3A} × {current GPT, Gemini, Claude} after changing model names.
  - External-validity limit: the saturation that motivates the paper comes from leaderboard systems that cannot be rerun (for example MAI-UI's AndroidWorld record is reported for the 235B variant, while only the 8B and 2B weights are released, per the MAI-UI README). The audit will cover reference scaffolds with current models and small open agents, not the leaderboard top.

  - **API cost, order of magnitude.** Assumptions (mine, to be re-measured in a 20-episode pilot): M3A makes two model calls per step, each carrying a screenshot and the UI-element list, about 10–15 k input and 0.4 k output tokens per step; about 20 steps per episode (step budget is 10 × complexity; the 116 optimal paths sum to 976 steps). That is roughly 0.25 M input and 8 k output tokens per episode. Episodes: 116 × 3 × 5 = 1,740 single-task runs, plus about 1,500 leg-runs for compositions (≈ 40 compositions × 2–3 legs × 3 runs × 5 agents) ≈ 3,200; with 3–4 of the 5 agents on APIs, 2,000–2,600 paid episodes ≈ 0.5–0.65 B input tokens. T3A is roughly half of M3A. The LLM-verifier baseline (re-grading ~2,000 passes with ~25 k tokens each) adds well under $300. Seeded faults and gold runs cost no API calls. Prices change; re-check before budgeting.

  **F6. Scripted gold policies — none are shipped.**
  - A repository-wide search for oracle/scripted/reference solutions finds only checkers (`initialize_task`, `is_successful`, `tear_down`). `tools.py` offers three helpers (`click_element`, `open_web_page`, `send_sms`); `human_agent.py` is manual play. MobileWorld ships none either.
  - Per-template UI scripting (uiautomator2/Appium, or AndroidWorld's own `JSONAction` + accessibility tree): straightforward for form-style CRUD in Simple Calendar, Pro Expense, Broccoli, Markor, Files and Settings (tens of lines each, parameterised); fragile for date/time pickers, first-run pop-ups and permission dialogs; hard for OsmAnd, drawing, camera, audio, VLC and the browser games. A set of ~15–25 scripts for the pairs in F3 is realistic; 116 is neither realistic nor needed.
  - Shortcut and its limit: the benchmark's own `add_rows`/`file_utils` can inject a correct end state directly. That calibrates checker specificity, but it bypasses the app, so it does **not** exercise the side writes the noise mask must learn. The mask needs UI-driven round-trips.
  - Step 5 as written ("faults produced through the app UI by script", six modes × checker families) multiplies the scripting to roughly 70 fault scripts. Inject at state level and confirm the app renders the state, or restrict to three families.

  **F7. Second benchmark — which are really public.**
  - **MobileWorld** — public, Apache-2.0, actively maintained: <https://github.com/Tongyi-MAI/MobileWorld> (arXiv:2512.19432). 201 tasks, 20 apps; privileged Docker-in-Docker container with a rooted Pixel 8 API 34 AVD and self-hosted Mattermost, Mastodon and a shop backend; image `ghcr.io/tongyi-mai/mobile_world`; needs Linux + KVM (WSL2 documented, macOS not yet). Each task starts from an AVD snapshot. Verification mixes text answers, backend database queries, adb inspection and app callbacks. Server-side state exists but is self-hosted, hence observable — at the price of a second observer for PostgreSQL-backed services with their own noise (timestamps, counters, job queues). Exclude tasks that need live internet (`chrome/check_weather.py` calls open-meteo; a GitHub lookup task), MCP tasks (need DashScope/ModelScope keys) and user-interaction tasks (need a simulated-user LLM). The changelog records a Mattermost token-expiry bug that produced false negatives — a reminder to run gold controls first. **Best candidate.**
  - **AndroidLab** — public, MIT, last commit Aug 2025: <https://github.com/THUDM/Android-Lab>. 138 tasks, nine apps including proprietary ones (Bluecoins, Zoom); Docker files distributed via a Google Drive link; result generation uses a judge model. Checkers are not state checkers in the sense needed here. Not recommended.
  - **MobileSafetyBench** — public, Apache-2.0: <https://github.com/jylee425/mobilesafetybench> (arXiv:2410.17520). About 26 evaluator modules; API 34 AVDs with emulator snapshots; Appium + adb; several checks read SQLite (SMS, calendar, PhotoNote). APKs must be fetched by hand, two of them from APKPure (PhotoNote, Stock Trainer) and a bank app from a personal GitHub repo. Few tasks per app, so little statistical room for "diff ⊆ gold diff".
  - **MobileWorldSafety** (arXiv:2608.17659) — 142 risk tasks on MobileWorld's infrastructure; the paper points only to an anonymised code link, and I found no permanent public repository; ambiguous runs go to an LLM judge. Do not make the plan depend on it.

  **F8. Baseline code availability.**
  - arXiv:2610.09142 — **available**: <https://github.com/OpenAdaptAI/side-effect-loopholes> (protocols, evidence, `reproduce.py` that recomputes the counts offline). It targets AppWorld and WorkArena (the latter needs a ServiceNow instance). For C3 the method must be re-implemented on Android; the paper's own applicability list requires a passing reference solution per task, which AndroidWorld lacks — the gold scripts of F6 double as that input.
  - arXiv:2609.22220 — artifact named KernelBench-M; a dataset `Elfsong/KernelBench-M` exists on Hugging Face. GPU-kernel domain, measured on one H100. Nothing to reproduce for a mobile paper; cite for the witnessed-denominator design only.
  - Agent-Diff, arXiv:2602.11224 — **available**, MIT: <https://github.com/agent-diff-bench/agent-diff> (the second URL printed in the paper's appendix, `agent-diff/agent-diff`, does not resolve publicly). Containerised Slack/Box/Linear/Calendar replicas on PostgreSQL with before/after table snapshots. It is the easiest non-mobile transfer target, but its grader already enforces a closed-world diff, so expect few wrong passes there; AppWorld (which ships reference solutions) is the more informative transfer check. For baseline (2) on Android nothing transfers; expected diffs must be hand-written.
  - EffectMatch, arXiv:2609.31301 — **no code link found** in the pages I could read; it builds on public MCPMark, STATE-Bench and ToolSandbox. It is a runtime commit gate rather than a checker audit; "EffectMatch-style" means own implementation. Drop it as a named baseline or describe it as inspiration.
  - Not checked: code for Sun (Research Square rs-10665114).

  **F9. Retained post-state.** The card's own citation (arXiv:2605.10448) says AndroidWorld records do not keep post-state. Public trajectories (including MobileWorld's viewer) are therefore unusable; every agent run must be produced in-house with the observer attached. This is a cost item, not a blocker.

  **F10. R3 (commutation).** Running A;B and B;A with a stochastic agent yields two different but possibly valid end states. Without an identical start (AVD snapshot, see F2) and a gold union state, R3 produces no certificate. I would drop R3 from the core.

- Riskiest technical dependency:
  A **state observer plus chained-leg harness whose masked diff is empty on scripted gold round-trips**, built on a benchmark that (i) wipes and reseeds app state at the start of every task, (ii) ships no reference solutions, and (iii) offers only about ten natural inverse pairs, several of whose checkers already contain an in-table frame check. If the mask cannot reach ≤ 2% false alarms without masking away ids, counters and timestamps that real violations also touch — or if the surviving pairs yield too few violations for a clustered bound — C1 is unprovable in both directions and C2–C3 inherit the problem. Everything else (emulator, agents, API budget, annotators, baselines) is obtainable.

- Minimal viable version:
  AndroidWorld only, one KVM host, observer limited to benchmark-app databases, SMS/contacts providers, shared storage and settings.
  1. Relations: **R0 read-only** on the 19 information-retrieval templates (single leg, unmodified initialisation) and **R1** on 8–10 inverse pairs (calendar, expense, recipe add/delete; Markor create/delete; Markor and Files move/move-back; Wi-Fi and Bluetooth toggles); R2 on the toggles for free. No R3.
  2. Controls: ~15 UI gold scripts, each round-trip run K ≥ 20 times; half to fit the mask, half held out for the false-alarm rate; planted unrequested writes for the ≥ 90% detection precondition.
  3. Agents: M3A with one strong and one cheap API model, T3A with the cheap model, optionally one 8B open model (MAI-UI-8B or UI-TARS-1.5-7B); 3 seeds. About 450–600 episodes, tens to a few hundred dollars.
  4. Arbiter: two annotators adjudicate all flagged passed runs and an equal-sized random sample of unflagged ones, blind to the flag.
  5. Leave out: seeded-fault calibration (C4), second benchmark, safety variant, non-mobile transfer.
  This still tests the key insight — whether a cross-task (or read-only) relation certifies wrong or extra effects among checker-passed agent runs at a rate distinguishable from the gold false-alarm rate, with flag precision ≥ 0.8.

- Ethics, licences and disclosure:
  - Emulator-only, synthetic data generated by the benchmark, no real accounts and no human subjects for AndroidWorld. Annotators label state diffs of synthetic data; state this in the paper. Do not use MobileWorld's real-device mode.
  - Licences: AndroidWorld, MobileWorld and MobileSafetyBench are Apache-2.0; AndroidLab and Agent-Diff MIT; the open GUI models listed are Apache-2.0 or MIT. The Android system image falls under Google's SDK terms and the bundled apps carry their own open-source licences, which I did not check one by one: **release scripts, diffs and masks, not AVD images, snapshots or APKs.**
  - Screenshots sent to API providers contain only synthetic content. SMS and calls stay inside the emulator modem; the emulator does have network access, so for any safety-variant run block egress or confirm that injected links and numbers are inert.
  - Safety variant: MobileSafetyBench includes harmful instructions and MobileWorldSafety injected phishing-style content. Use only the existing tasks inside an isolated emulator, publish no new attack payloads, and do not apply R1 there (asking an agent to perform a risky action and then undo it is not a meaningful or prudent test) — only the "diff ⊆ gold diff" check. Two MobileSafetyBench apps come from a third-party APK mirror; that is a licence and integrity concern worth avoiding.
  - Disclosure: confirmed checker defects are bugs in public benchmarks. File them with the maintainers before the paper appears (arXiv:2610.09142 reports having e-mailed the benchmark authors); report rescored rankings with care, since they concern third parties' systems.
  - The constraint "attack research only in a synthetic sandbox" is met. The LLM-use policy of the venue applies to the manuscript, not to this design.

- Likely reasons for rejection (feasibility-related):
  1. Too few composable pairs: about ten template clusters give wide task-clustered intervals; neither "lower bound > 3%" nor the "well-powered negative result" may be reachable.
  2. Verdicts on leg 2 are produced under a modified initialisation; a referee can say the audited object is no longer the shipped benchmark and that violations are harness artefacts.
  3. The mask is tuned on the same few apps it is evaluated on, and what it hides (ids, counters, timestamps) overlaps with what real duplicate-then-delete behaviour changes; most surviving violations may be benign residue.
  4. The SQLite families already check the frame inside the target table, so the instrument may fire mainly on file-based and toggle tasks — a narrow finding.
  5. The agents audited are reference scaffolds and 8B open models, not the leaderboard systems whose near-saturation motivates the paper.
  6. A state-reading LLM verifier over the retained post-state (the card's baseline 1) covers all 116 templates with no scripts; if its precision is comparable, the relation instrument looks dominated in coverage and cost.
  7. Scope not delivered: second benchmark, safety variant and transfer check promised in the sketch but dependent on a heavier observer (MobileWorld backends) or on code that is not reliably public (MobileWorldSafety, EffectMatch).
  8. Seeded-fault arm: per-cell sensitivity of 0 or 1 (already listed in the card) plus ~70 UI fault scripts.

- What would make this a clear accept:
  1. A pilot, before any agent run, on a real KVM host: mask false-alarm ≤ 2% on ≥ 200 held-out gold round-trips and ≥ 90% detection of planted writes, with the mask rules published.
  2. A written applicability rule with a coverage table reaching at least a third of the suite, obtained by adding R0 (read-only tasks) to R1/R2 rather than by authoring new inverse tasks.
  3. A check that the chained-leg harness does not change verdicts: gold round-trips pass both legs at the same rate as the unchained tasks.
  4. At least one current frontier API model and one open 8B agent, three seeds, with all post-states retained and released.
  5. The same passed runs graded by the LLM-verifier baseline, with precision, recall and cost side by side.
  6. A port of R0/R1 to MobileWorld's offline GUI-only tasks to show the harness is not AndroidWorld-specific.
  7. Violations attributed to a leg and graded for severity by two annotators, with the defects filed upstream and the observer, harness and gold scripts released under Apache-2.0.
  8. C4 kept only for three checker families, clearly labelled as a secondary, preregistered test.
